## Transaction and crash boundaries

Ingress verifies bytes, validates minimal routing, then commits one receipt under the existing domain advisory lock before200. No Shopify token is required. Processing claims one row with `FOR UPDATE SKIP LOCKED`, records a60second lease/fencing token and increments attempts. Network-free export/deletion acquires the same authentication lock used by managed SDK credential rotation, then the lifecycle domain lock used by ingestion and merchant actions, with a30second transaction bound. This fixed lock order lets an earlier credential write finish before erasure removes its credentials. The deletion cutoff is calculated inside that locked transaction and covers the installation actually observed there. Failure retains work and blocks relevant ordinary access; exhausted jobs remain visible for operator escalation.

Deletion appends authenticated **keyed hashes only** to the independent journal and fsyncs before deleting rows. The database marker, cascade and receipt completion commit together. A crash after fsync but before commit can over-block temporarily; retry/sweep completes deletion. A late snapshot writer must reacquire the domain lock and check current deletion state. Sync skips erased IDs and never treats their absence as usable new order evidence.

The journal is outside database backups and must stay newer than a restored backup. Missing/truncated/tampered journals fail closed. Signatures cannot detect replacement with an older valid journal or removal of an entire valid suffix; immutable/current external custody remains a production dependency, not a claimed solved property. Ledger expiration is deliberately not automated pending reviewed backup/replay horizons. Hashes are sensitive metadata.

An inaccessible retained snapshot puts export preparation into retry, never a false empty completion. Once erasure has actually removed it, a newly prepared export can be empty. Download/handoff guards inspect the actual encrypted prepared evidence, so a requested-but-already-erased ID does not invalidate that legitimate empty artifact. The added synthetic regression reproduces both states.

## Actual inventory reconciliation

Earlier architecture statements that privacy is intake-only are historical and superseded by this local P09 implementation. Approved order fields, both rule semantics, original30day retention and monitoring boundaries are unchanged. No financial/fulfillment status, Customer.id profile, contact/address, `read_all_orders` or Shopify mutation added.

Additional privacy-only metadata: optional HMAC customer-routing hash, request/delivery/topic/shop routing, processing lease/attempt/error/time, encrypted prepared export, expiration and encrypted confirmed-handoff actor/time/reason. Customer association uses the signed order lists because no customer-ID/order mapping is collected. Raw customer fields are discarded; an email-only customer with an explicit empty list produces a genuine empty export for this inventory. Completed redaction retains no plaintext erased order list. Unresolved requests stay visible rather than being presented as completed compliance.

Privacy receipts and deletion hashes are restricted operational retention exceptions for fulfillment and anti-resurrection; this is a technical safety policy requiring owner/provider review, not an invented legal obligation. Proposed encrypted backups≤7days and logs≤7days are **not verified deployments**. Physical volume/database transport encryption is still unverified.
